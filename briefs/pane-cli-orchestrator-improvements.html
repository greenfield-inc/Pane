Making the Pane CLI easier for orchestrators

Lessons from running the BloomText frontend refactor through runpane: 48 PRs, up to 3 parallel workers, one orchestrator restart. Written by the Session orchestrator, 2026-09-27.
Bottom line: Pane made long, parallel work durable and visible, and that was worth it. But every worker cost me about ten manual steps, and roughly a third of my attention went to plumbing: prompt delivery, watcher upkeep, reading results off the screen. Five changes would remove most of that: create a Pane on any base branch with the prompt file in one call, deliver long prompts intact and report delivery accurately, return a structured completion report, a Session-wide watcher that follows Pane membership, and archive that removes adopted worktrees.

What one worker cost me today

Proposals, by priority

P1Create a Pane on any base branch, with the prompt, in one call

What happened
panes create makes its own worktree but had no way to choose the base branch, and every worker had to start from release/frontend-modernization. So for 25+ workers I ran git worktree add, then panes adopt --launch, then waited, read the screen and submitted the prompt separately. adopt has no --initial-input-file.
Proposal
  • panes create --base <ref> --branch <name> for Pane-managed worktrees off any branch.
  • --prompt-file on both create and adopt, delivered after readiness with the same delivery guarantee as below.
  • --unset-upstream or a sane default, so new branches don't track the base branch.
runpane panes create --repo BloomText --base release/frontend-modernization \
  --branch agents/w5a-web-conversation --agent claude --folder "Frontend Refactor" \
  --prompt-file prompts/w5a.md --source agent --json

P1Deliver long prompts intact, and report delivery accurately

What happened
  • Truncation: a ~40-line prompt sent with panels submit --input-file arrived cut off at the start; W3a's agent said its "message arrived cut off at the start". After that I only sent one-line prompts that pointed to a file.
  • False "not delivered": about 7 times, verifiedSubmitted: false (sometimes with a blocked "still in the composer" hint) came back while the agent had already taken the turn or queued it ("Press up to edit queued messages"). Each time I had to read the screen to avoid a double send.
Proposal
  • Send long input as one paste (bracketed paste, or a file attachment the agent opens), and verify it by comparing a hash or length against what the agent's session log recorded.
  • Replace the boolean with a state: delivery: "taken" | "queued" | "in-composer" | "unknown", taken from the agent's transcript, which Pane already has for resume.
  • Built-in --as-file-pointer: Pane writes the prompt to the Pane data dir and submits "Read and follow <path>". It's the workaround I used, and it's reliable.

P1Give back a structured completion report, not a screen to scrape

What happened
Background subagents handed me a final report automatically. Pane workers didn't: every READY meant panels screen --limit 50, then reading the last ~2,500 characters of terminal text, then parsing out the PR number, head SHA and state. READY also fired for workers that had already finished (C2, C5a, C5b after their PRs merged).
Proposal
  • A worker-side command: runpane report --state ready|blocked|failed --pr 747 --head fc5dce9 --summary-file report.md. The prompt can tell the worker to call it.
  • A agent.done watch event that carries that report (state, PR, head, summary path). BLOCKED events should carry the question.
  • panels last-message --panel … --json: the agent's final message as clean text, without the terminal chrome.

P1One Session-wide watcher that follows Pane membership

What happened
  • Re-arming: I re-armed the watcher about 20 times, whenever a Pane was added or finished, and every 30 minutes when my harness's monitor expired. Each time meant stopping the old watch and rebuilding the --pane list.
  • Name limit: the documented cursor name session-<session-id> fails with "must contain 1-64 letters…", because orchestration Session IDs are about 70 characters.
  • Filtering: the docs say to filter out HEARTBEAT, but --json emits _heartbeat, _ok and _reset. My first filter let heartbeats wake me every minute.
Proposal
  • runpane watch --session <id> --follow: tracks associated Panes live, drops archived ones, and needs no re-arm when membership changes.
  • Derive cursor names that fit, for example hash long IDs automatically, and fix the documented example.
  • --no-control-lines (or --quiet) to suppress heartbeats, ok and reset lines, and a note in the JSON docs listing which kinds are control lines.

P2Archive should be able to remove the worktree it adopted

What happened
For adopted Panes, panes archive --dry-run returned safetyCheck.performed: false and left the directory in place. Cleaning up 45 worktrees meant my own dirty and unpushed checks, then checking each branch against its merged PR, then git worktree remove. That took about 12 minutes of node_modules deletion, and my command timed out.
Proposal
panes archive --remove-worktree for adopted worktrees, using the same safety evidence it already has: uncommitted, untracked and unpushed changes, plus "head merged via PR #n" when the remote branch was deleted after a squash merge. Also a bulk form, panes archive --session <id> --merged, that deletes large folders in the background.

P2Locks for shared test resources

What happened
V4 and V5 shared the testing account's single "approve guest" banner and approved each other's guests during two-browser call tests. They worked it out through a cross-session message, which was impressive, but V5 then sat idle for about 40 minutes. The iOS simulator was a similar shared resource.
Proposal
runpane lock acquire <name> --ttl 30m and release, visible in sessions overview. The orchestrator can name locks in prompts ("hold testing-account-video while running call QA"). Per-worktree port allocation already works well and fits the same idea.

P2Session-level work items, not a hand-kept ledger

What happened
I kept .agent/ledger.json by hand, 60+ items mapping phase to Pane, panel, worktree, branch, PR, state and notes, and edited it after every event. The Session record in AGENTS.md stayed empty, because I never had a natural reason to call sessions update.
Proposal
runpane sessions items add|update|list on the Session record, with fields for Pane, PR and state, and optionally linked to GitHub so the PR state is filled in automatically. sessions overview would then show the whole board, and a restarted orchestrator could recover in one call.

P3Smaller fixes

  • --pane-dir: the runtime context says to pass it on "every command that accepts it", but most commands reject it with "only valid with install daemon". Accept it everywhere, ignoring it where it doesn't apply, or have agent-context say which commands take it.
  • Ghost suggestions: panels screen shows Claude's grey composer suggestions ("❯ merge it", "❯ delete the branch") as if they were typed text. hasUndeliveredText is correct, but tag ghost text in the screen output so it's never mistaken for input.
  • PR events: a pr.conflicted / pr.checks watch event for PRs opened from Session Panes. I hit about 12 counts-file conflicts after merges and found each one by polling gh.
  • Panel for a Pane: panes adopt returned sessionId (the Pane) and panelId, but paneId was null at the top level. Include both consistently.

Addendum (2026-09-27): issues found after this brief was written

P1Delivery into agent-farm panels silently fails

What happened
The Pane "Pane Session Management Improvements" runs its agent in a terminal panel started by agent-farm (title "agent-farm run free-range"). For that panel:
  • panels screen reported composer: {isPresent: false, hasUndeliveredText: false} even though a normal Claude prompt box (❯) was on screen.
  • panels submit --input-file returned ok: true, verifiedSubmitted: false with no blocked hint, and the text sat unsent in the prompt box.
  • panels submit-composer --strategy auto returned ok: true and still didn't send it. Only --strategy enter worked, and only while the agent was idle. While it was running background Explore subagents, --strategy enter also left the text unsent, so a follow-up couldn't even be queued.
Because hasUndeliveredText was false, the documented "resubmit only with proof of non-delivery" rule couldn't be followed from structured output. I had to read the raw screen text.
Proposal
Detect the composer by content (the agent's prompt glyph and box), not only by the panel's launch type. When a panel was launched by a wrapper (agent-farm, custom --tool-command), resolve the underlying agent type and use its submit strategy. When detection fails, return blocked: {kind: "composer-unknown"} instead of a silent ok: true. submit-composer --strategy auto should fall back to enter when the text is still visible after the first attempt.

P2Panel and Pane metadata don't identify the agent

  • No agent type: panels list returned agentType: null for the agent-farm panel. An orchestrator can't tell which terminal is the agent without guessing from the title.
  • Wrong status: panes list showed that Pane as status: "stopped" while its agent terminal was live and waiting for input.
  • Proposal: record the agent type (and the wrapper) on the panel at launch, and derive Pane status from its panels' activity.

P3More small fixes

  • Unknown commands: runpane agent-context --command "<unknown>" --json printed non-JSON instead of a JSON error listing the valid commands. I found the real command, panes archive, by scraping the full context. Return {ok:false, code:"unknown_command", candidates:[…]}.
  • Why archive skipped removal: panes archive --dry-run on an adopted Pane returned safetyCheck: {performed: false} with no reason. Add reason: "externally-managed-worktree" and say that the directory will be left in place.
  • READY timing: with the recommended --settle 180000 --min-interval 600000, a READY can arrive up to about 13 minutes after the turn ended. That's fine for overnight runs, but slow when a person is waiting. Document a "user is present" profile (e.g. --settle 60000 --min-interval 120000) in pane-orchestrator.
  • Busy-agent wording: when the agent is busy, a submitted prompt is queued ("Press up to edit queued messages"). panels submit should report delivery: "queued" (see P1 delivery state) rather than verifiedSubmitted: false.

What worked well (keep it)

  • keepDurability: when my orchestrator session restarted, two background subagents died mid-task. Pane workers would have kept running, and after the switch they did.
  • keepVisibility: every worker was a real workspace you could open, watch or step into.
  • keepCross-session messaging: V4 and V5 coordinated on their own.
  • keepAssociation: association.ok on every create or adopt, plus the automatic Session membership.
  • keepArchive safety checks and --dry-run, and panels open --file for showing pages beside the chat.
  • keepSettle and backoff flags on watch: once filtered properly, wake-ups were infrequent and meaningful.

What I'd do differently next time (no Pane changes needed)

ChangeWhy
Use Panes from the first workerThe first ~20 workers were background subagents; the restart killed two of them.
Always dispatch a one-line pointer to a prompt fileAvoids truncation, and a quoted heredoc avoids shell mangling (one of my prompts lost a line to backticks).
Scope work with the project's own tooling (pnpm ratchet --list), never a text grepMy connect( grep matched comments; C5a found 11 of its 14 "files" were already converted.
Make shared bookkeeping files merge-friendly before fanning outThe single counts file conflicted on almost every merge.
Point every smoke test at staging explicitlyOne production-build smoke test sent three unauthenticated reads to the production API.
Put one "wait for your lock" line in every prompt that touches shared accountsThis would have prevented the V4/V5 banner collision.

Evidence: Session ledger (.agent/ledger.json), prompts in prompts/, and worker reports in reports/ inside the BloomText Frontend Refactor Session folder. Counts: 48 PRs merged into the release branch (#499–#753), about 25 Pane workers, 19 archived Panes, 45 worktrees removed.
