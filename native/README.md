# Pane for iOS and Android (Expo)

`native/` is the React Native companion app for Pane: Expo SDK 57, React Native 0.86 (New Architecture, Hermes), Expo Router, a dev client, TypeScript strict and the React Compiler. It sits beside the Capacitor shell in `mobile/`, which keeps working, and uses the same bundle ID (`com.dcouple.pane.mobile`).

The app talks to a Pane host (daemon) over its HTTP API: `POST /invoke`, the `GET /events` SSE stream and `/health`. It uses the shared client in `shared/remoteClient`. The bearer token goes only in the `Authorization` header, never in a URL.

## Run it

Use Node 22 and pnpm from the repo root (`pnpm install` installs this workspace too).

```bash
cd native
export PATH=/opt/homebrew/opt/node@22/bin:$PATH
npx expo run:ios --device "<your simulator>" --port 8137   # builds the dev client, starts Metro
npx expo run:android --port 8137                           # needs JAVA_HOME (JDK 17) and ANDROID_HOME
pnpm start                                                 # Metro only, once a dev build is installed
```

`ios/` and `android/` are generated by `expo prebuild` and are not checked in. `targets/` holds the iPhone notification service extension, which `@bacons/apple-targets` adds to the generated project. Change native settings in `app.json` or a config plugin, never in those folders. Add a native library with `pnpm add <pkg>@<sdk-57 version>` (see `npx expo install --check`), then rebuild the dev client.

iOS builds use Expo's scene lifecycle through `expo-build-properties` with `ios.enableSceneSupport: true`. This requires Expo 57.0.23 or newer. Apps built with the iOS 27 SDK fail at launch on iOS 27 without it ([Apple's migration guide](https://developer.apple.com/documentation/technotes/tn3187-migrating-to-the-uikit-scene-based-life-cycle), [Expo setup](https://docs.expo.dev/versions/v57.0.0/sdk/build-properties/#pluginconfigtypeios)). Regenerate the iOS project after changing this setting; adding only a scene manifest does not move React Native startup to the scene delegate.

## Try a demo

**Try a demo** on the welcome screen runs the app against a sample Pane host that lives in the app (`src/features/demo/`), so App Store and Play reviewers, and anyone without a computer yet, can use every screen. `createDaemonClient` gives any profile whose address ends in `.demo.invalid` an in-memory `fetch` and event stream instead of the network, so the real client and screens run unchanged. The demo keeps its state in memory: answering a question, creating a Pane or typing in a terminal changes what later reads return. It is never saved to the Keychain, asks for no notification permission, and ends on **Exit Demo** (the **Demo** badge on the home header, or Settings), a relaunch, or pairing a real computer. Uploads, voice and glasses say they need a computer. The sample content is in `demoData.ts`. A dev build started with `EXPO_PUBLIC_PANE_CAPTURE=1` hides the **Demo** badge for store screenshots; release builds always show it.

Settings and the welcome screen link to the privacy policy at `https://runpane.com/privacy#phone-app`.

## Machines

Home shows the Pane logo, then a row of filter chips: **All** first (once two or more machines are saved), then a chip for each machine in saved order: the saved ones, plus your own Tailscale machines that **Your computers** lists as Ready or Needs password. The selected chip is filled, and stays selected across relaunches. Chips show the first 10 characters of a name; VoiceOver and TalkBack read it in full. Tap a machine's chip to switch to it; a machine you never connected to connects in that tap and is saved, asking for its password first when it needs one. Tap the selected machine, or long-press any chip, for **Machine details** (address, status, color, Sign out). With one machine the chips hide. Pull to refresh reloads the list.

**All** lists every saved machine at once: their Notify questions and permission requests under **Approvals**, then every Pane and Session by newest activity, each with its repository, its Session, how long ago it was active and its machine's badge. Search covers every machine's rows. The phone reads the machines it isn't on without connecting to them (five reads every 15 s while All is on screen and the app is in the foreground, each with its own 8 s deadline), so a slow or offline machine never holds up the others. A machine that stops answering dims; its rows stay, dimmed, under "<machine> went offline at 9:14. Its rows are from then." with Retry. Opening another machine's Pane, Session or approval switches to that machine first; Yes and No under another machine's prompt answer straight to it, the way alert buttons do, without switching. Only the current machine's rows swipe.

The + at the bottom right (and a repository's own +) opens **New**: a Session/Pane toggle, the machine to create on (it starts on the machine New last created on, remembered on the phone), then that machine's form, with its repositories, branches and agents. Create goes straight to that machine; then the phone switches there and opens what it made.

Each machine has a color and its OS logo (`src/features/machines/`). The color comes from the machine's Tailscale name, or its label when paired with a code, and is never stored: names settle clashes alphabetically, so pairing order never changes a color. The logo is solid when reachable, pulses while the current machine reconnects (one 1.6 s rhythm; dimmed instead under Reduce Motion), and is dimmed when the machine can't be reached.

Settings opens on the current machine, with every other machine under **Switch to** and **Add a machine** (scan a QR code, paste a connection code, or Tailscale's Your computers). **Composer** is saved on the current machine, which its title names; **General** (Notifications, Glasses, Autocorrect) covers every saved machine. On home, swipe a Pane or Session right to pin it, and left to pause or resume it or archive it; VoiceOver and TalkBack offer Pin, Pause or Resume, and Archive as row actions. A paused Pane or Session is grayed out with a pause glyph where its status dot goes. Opening a paused tab shows its last screen under a **Paused … · last screen** bar with **Resume**, and starts nothing; when the computer's Settings turn on resuming paused Panes on open, opening the tab resumes it.

## Approvals

Home lists what waits on you under **Approvals**, newest first. A sort menu, remembered on the device, chooses **Most recent** (flat, the default), **By Session** (the Session's name and its machine's mark, with **Not in a Session** for the rest) or **By project** (with **No project** for the rest); items from hosts older than Approvals land in those last groups, and each group sits by its newest item. Answers still held for Undo stay listed as "Sent: …". Each question's row shows the card's subtitle (its context, two lines at most) and, after you reply, where the reply stands in the words every surface uses (`shared/approvalStatus.ts`: "okta-sso-account is reading your reply", "… is getting more context", "Updated · ready again", "Taken as your answer: …"). An approval whose reply an agent is reading or asking about moves to **With the agent · N** below what waits on you, and out of the counts, until it comes back ready again. A worker's question is an ordinary card with an answer box from the start, with one set of buttons per question, each starting on its recommended choice. A machine that isn't online collapses to one row ("<machine> offline · N waiting · they come back when <machine> is online"), and stale items and today's answered and closed items sit in collapsed **Stale · N** and **Done today · N** groups at the bottom; none of these count. The approval screen's **Summary** opens the approval's Summary page (`notify:summary-page`) in a WebView with JavaScript off that refuses every navigation. Cards show who asked, what they're connected to and who acted (`shared/approvalReceipts.ts`), with Close, Override and Reopen sent to the machine holding the item.

Tapping one opens its approval screen (`src/app/approval/[notifyId].tsx`): the card on top with "1 of N" and Next, its related files and pages as chips (tapping one opens it as a tab below), and its answer controls; below it, the Session's tabs and orchestrator chat for an orchestrator's item or a fallback, or the asking Pane's tabs for any other. Type there to ask about the item. An item answered elsewhere steps to the next one, or back home when none is left. A question alert's tap opens the same screen, using the `sessionPaneId` the alert carries when the question can't be read.

## Point it at a host

The app opens on the camera the first time: scan the code that **Pair a phone** shows in Pane on your computer. The QR is `https://runpane.net/pair#s=<secret>&c=<computer>&n=<name>`, a universal link (iOS) and app link (Android), so the phone's own camera opens the app too, on **Pair with <computer>**, where one tap pairs. The phone trades the one-time secret at `https://<computer>.runpane.net/pair/exchange` for its own token and saves that computer and every computer linked with it, then links the new computer with the phone's other relay computers, with no prompt (`shared/remoteClient/relay.ts`). Each connection to the computer refreshes the list: it saves computers linked since. Under the camera: **Paste a connection code**, **Use Tailscale instead** and **Try a demo**. **Settings → Add a machine** opens **Add a computer**: **Scan a QR code**, or **Paste a connection code** and **Use Tailscale**. Errors say "This code was already used", "This code expired" or "Can't reach <computer>".

A relay computer reconnects like any other (the 10-second grace and the one-line bar), but the app never stops retrying while it is open, at most 30 s apart. When the relay says the computer is asleep, the bar says "Asleep since 9:40". A computer that removed the phone is the one hard stop: the bar says so, with **Pair again**. Pages on a relay computer load through the one-time address it hands out (`relay:client:preview-address`). The connection goes through Pane's servers until the native networking module adds same-network and direct paths; `relayBaseUrl` is where it picks the address.

For your computers over Tailscale, sign in to Tailscale on the phone and computer, then tap **Use Tailscale instead** on the welcome screen (or **Settings → Add a machine → Use Tailscale** after connecting). Enter the **Address** shown in desktop **Settings → Remote Access → Access**, tap **Find computers**, then **Connect**. Enter the computer's password when asked. **Use another computer** lets you change the address if that computer is unavailable or you switch tailnets. Saved profiles stay bound to their original tailnet.

The phone asks a computer on its own Tailscale login for the tailnet list because it cannot run `tailscale status` itself. Other users cannot request that computer's discovery view, even when it allows everyone on the tailnet to connect. Native requests use the Workspaces listener on port 8443. Push notifications and shared integration keys work over this connection for the computer's owner; another Tailscale user the computer lets in is refused. Browsers and the PWA keep using connection codes: the Workspaces listener refuses requests with an `Origin` header, except the Pane glasses app, which Settings › Glasses pairs with a per-device token ([Even G2 glasses](../docs/EVEN_G2_GLASSES.md)).

You can also pair with a host through a one-time `pane-remote://` connection code, pasted or scanned from a QR code. For development, run an isolated host with its own data directory and port, so you never touch the Pane you use day to day:

```bash
# from the repo root
pnpm run build:main && pnpm run electron:rebuild
D=$HOME/.pane_rn_dev
node main/dist/main/src/daemon/setupRemoteHostCli.js --pane-dir $D --label "RN Dev" \
  --listen-port 42157 --prefer-tunnel ssh --no-install-service --no-tailscale-serve   # prints the code
PANE_DIR=$D pnpm exec electron ./main/dist/main/src/daemon/headless.js --pane-dir $D
```

The simulator reaches `http://127.0.0.1:42157` directly. For the Android emulator, forward the port first: `adb reverse tcp:42157 tcp:42157`. Non-loopback hosts must use HTTPS (Tailscale Serve or an HTTPS proxy), and a phone reaches them over Tailscale, an SSH tunnel or that proxy.

To add projects and panes to the dev host, use the RunPane CLI against its data directory, for example `node packages/runpane/dist/cli.js repos add --path <repo> --yes --pane-dir $D`.

### End-to-end tests (Maestro)

Flows live in `.maestro/`. Start Metro on port 8137 with the dev build installed and the dev host running, then:

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home
export PATH=$JAVA_HOME/bin:$HOME/.maestro/bin:$PATH
maestro --device <simulator-udid> test -e CONNECTION_CODE="$(cat ~/.pane_rn_dev/connection-code.txt)" .maestro/sign-in.yaml
```

`subflows/launch-dev-client.yaml` clears app state and the Keychain, opens the dev client against `127.0.0.1:${METRO_PORT}` and gets the dev menu out of the way. `subflows/sign-in.yaml` pairs with `CONNECTION_CODE`. Start a feature flow with `- runFlow: subflows/signed-in.yaml`, which runs both. It uses Metro on port 8137 unless you pass `-e METRO_PORT=<port>`. Pressable rows merge their text for accessibility, so match rows by `testID` or a regex such as `"fix-login-bug.*"`.

`demo.yaml` needs no host: it starts the demo, answers a question, uses a terminal, visits the other screens and exits. Run it without `CONNECTION_CODE`. `tabs.yaml` needs no host either: it opens a page, Explorer, the file viewer, Diff, Run script, an Editor tab and a placeholder in the demo.

`relay-pairing-link.yaml` opens a pairing QR's link and pairs; pass a fresh one as `-e PAIRING_URL=<https://…/pair#…>`.

`pause.yaml` pauses and resumes a new Pane and a new Session on a host with a repository and Sessions, with resuming paused Panes on open turned off (the default).

`terminal.yaml` needs a host whose first pane has a plain `Terminal` tab and a `Claude Code` tab, which is what `runpane panes create --agent claude` gives you. On a busy machine, set `MAESTRO_DRIVER_STARTUP_TIMEOUT=240000` if Maestro reports that the iOS driver was not ready in time.

## Tabs

A Pane or Session screen shows every tab in one strip, each with its type's icon: agents and terminals, then pages, then Explorer and Diff, then other tabs, then tabs that open only on the computer. A Session's agent chat comes first. Each type has its own view (`src/features/terminal/panels.ts` picks it):

- **Pages** (`src/features/browser/`) load in a WebView under an address row with back, forward, the address, reload and Open in Safari. A computer's dev server and HTML files load through the phone addresses it creates over Tailscale ([Browser tabs on the phone](../docs/SELF_HOSTED_REMOTE_DAEMON.md#browser-tabs-on-the-phone)). On a computer paired with a QR, they load through a one-time address the computer hands out instead. When those addresses are off or out of reach, an HTML file is read through the phone's own connection instead (`panels:read-browser-file`), so a self-contained page loads with a pairing code too. Entering an address saves it to the tab, so the computer's tab moves with it. Each case that can't load has its own screen: nothing listens on the port, pages are off on that computer, the phone is off Tailscale, the computer is offline, or its Pane is too old.
- **Explorer** (`src/features/files/`) lists the branch's changed files first, then browses the worktree one folder at a time, with a path bar back up and a search box; changed files carry their M, A or D badge. Files open read-only: code with syntax colours (highlight.js) and line numbers, Markdown rendered or as source, images up to 5 MB. Text over 1 MB and other binaries stay on the computer, with Copy path. **Editor** tabs open their file in the same viewer.
- **Diff** (`src/features/diff/`) lists the branch's changed files with their counts, against the same base as the desktop's Changes panel; tap a file for its patch. A patch too large for the phone says so. An Editor tab showing a file's changes opens its patch. Explorer and Diff share one read of the changes per Pane, refreshed when the computer's git status changes.
- **Run script** (`src/features/runScript/`) shows the Pane's script output and follows it live (`sessions:get-logs`, then `session-log` events), staying at the end until you scroll up.
- **Notes, Dashboard and Setup tasks** tabs are dimmed and say which computer they open on.

The phone follows the computer to a tab it brings forward (an agent's `runpane panels open`, for example) only when the phone draws that tab and it sits on the desktop's stage; Explorer and Diff live in the desktop's side panel, so the phone never jumps to them. Demo mode has a sample of every tab type (`src/features/demo/demoFiles.ts`, `demoPages.ts`).

## The terminal page

The pane screen runs xterm in a WebView. The page source is `terminal-web/page.ts`. `pnpm build:terminal-web` bundles it, with xterm and its CSS, into `src/features/terminal/terminalHtml.generated.ts`, so the WebView needs no network. Run it after changing the page or upgrading xterm, and commit the generated file. The page and the screen talk through the messages in `src/features/terminal/bridge.ts`. The scroll joystick scrolls the page's own buffer, except when a full-screen app is on the alternate screen or has asked for mouse events (Claude Code with `"tui": "fullscreen"`, less, vim, tmux): those keep no scrollback here, so the page sends them wheel input instead, as xterm does for a desktop mouse wheel.

`panes.yaml` creates a pane, searches, pins, archives and deletes it; it needs at least one repository on the host. `permission.yaml` answers a permission request; queue one first with `node scripts/request-permission.mjs <pane-dir> <pane-id>`, which stands in for the agent's permission bridge.


## The composer

The pane screen's text box holds every action: Attach, Paste, Shortcuts and Copy on the left, the mic and one Send/Enter button on the right. An empty box sends a bare Enter, which answers an agent's menu; with text, the button sends the text and then Enter. Each terminal tab keeps its own unsent text on the phone (per host, pane and tab, in `composer-drafts.json` in the app's documents folder), so it survives leaving the pane and restarting the app; sending clears it. Return on the phone keyboard sends too, the way Enter does in a terminal, and sending either way closes the keyboard; text with line breaks still arrives through Paste, dictation or Shortcuts. **Settings → General → Autocorrect** (on by default, kept on the phone) turns the keyboard's autocorrect and spell check on or off in the terminal box and in a chat tab's message box. A chat message is prose, so its box keeps sentence capitals and smart punctuation. The terminal box never capitalizes the first word, and swaps iOS smart punctuation (curly quotes, `—` for `--`, `…` for `...`) back to plain characters as you type, so commands still run. Only the keys you just typed are swapped, so text already in the box (such as a path from Paste) keeps its exact characters. Hold a tab for Close; a tab whose agent is still working asks first. Clear scrollback sits in the "…" menu. Copy shows the terminal's recent output as selectable text. Last 300 lines copies the host's clean scrollback (`terminal:getScrollbackClean`) to the clipboard and shows it.

Shortcuts live on the host, in its `terminalShortcuts` config, the same list desktop binds to ⌘⌥ (Ctrl+Alt) plus a letter. The bolt opens them as a filterable sheet; Settings › Shortcuts adds, edits, reorders, turns off and deletes them. The phone saves through `remote:settings:update`, which takes only `terminalShortcuts` (the whole list) and the voice keys, refuses any other field, and returns the refreshed `remote:pwa-affordances`. Every save emits `remote:settings-changed`, so open phones and desktop refetch. Hosts without the channel still serve the list to insert; saving there asks you to update Pane on the host.

The mic records through the host. When the host has the key for a mode, tapping the mic records. When it lacks one, the mic opens a sheet that asks for the one key the mode needs (live mode: Deepgram; recorded mode: fal). A host before v2.4.159 also needs OpenRouter; there the sheet asks for it and says to update Pane on the host. OpenRouter is an optional row: with it the host cleans up the transcript, without it the host returns the words as heard. The sheet saves the keys with `remote:settings:update`, and starts recording in the same tap. A live start from the sheet waits 2.5 s for Deepgram to accept the key, so a refused key shows on the sheet. Keys travel only in that request's body; the phone clears them after the save, and the host reports them only as set (`src/features/voice/VoiceSetupSheet.tsx`). Settings › Voice shows each key as Set or Not set and replaces it through the same channel. The phone also carries keys between the hosts it is paired with: on open, on return to the foreground, after a key save and when a host reports a settings change, it reads each host's keys with `credentials:shared:get` and writes the newest to the rest with `credentials:shared:apply`, keeping no copy (`src/features/hosts/SharedCredentialSync.tsx`, [Shared integration keys](../docs/SHARED_CREDENTIALS.md)). A recording runs up to 15 minutes. In the last minute the timer beside the mic counts down, with one tone and one haptic as it starts. Recording stops by itself after 30 seconds below -50 dBFS, keeps the text so far, and says why (`src/features/voice/recordingLimits.ts`).

The terminal's right edge carries the scroll joystick, a D-pad with Enter in its center, and Esc, Tab and ^C (Ctrl+C, which stops the running command). They rest at 18% opacity; touching any of them makes all of them opaque, and 3 s after the last touch they fade back together (`src/features/terminal/FloatingController.tsx`). The D-pad sits five rows above the bottom, clear of an agent's input box and status line, and hides when the terminal is too short for that, as with the keyboard up (`controllerLayout.ts`). The controller button beside the mic shows or hides them; the choice is kept on the device.

## Uploads

The paperclip in the composer sends photos, camera shots and files (any type, up to 50 MB each) to the host and inserts each file's host path at the cursor, the same path desktop's upload button pastes. Files go up in 128 KB chunks over `POST /invoke` (`terminal:upload-start`, `-chunk`, `-commit`, `-cancel`), so a slow or flaky link only ever resends one chunk: every reply carries the bytes the host has, and after a drop the phone calls `upload-start` again and continues from there. The host stages partial uploads in `<pane-dir>/uploads/`, deletes ones untouched for a day, and lands finished files in `<pane-dir>/images/` or `<pane-dir>/files/` through the same code as a desktop paste (`main/src/services/chunkedUploadStore.ts`, `main/src/ipc/panels.ts`). Hosts without these channels get the old single request, capped at about 12 MB. The upload loop is `src/features/upload/chunkedUpload.ts`.

## Notifications and links

**Push.** The host sends APNs and FCM alerts itself when an agent is blocked or finishes a turn (`main/src/daemon/mobilePushSender.ts`, operator setup in `docs/NATIVE_MOBILE.md`). The app registers the raw device token from `getDevicePushTokenAsync`, not an Expo push token, through `mobile:push-status` and `mobile:push-register`, with every saved computer: when the app opens or returns to the foreground, when the saved computers change, when key sync gives a computer the push key, when the open computer reconnects, and when the OS rotates the token (`PushRegistrationSync` in `src/features/notifications/usePushSetup.ts`). Each call is one request, with no workspace stream, so one computer that is off doesn't hold up the others. It asks for notification permission once, and only when a computer reports that delivery is set up. Settings › Notifications shows the "Needs input" and "Finished" switches, which apply to every computer and ride each registration. Until you change them on this phone, each computer keeps its own values, and the switches show what your computers had: a kind any computer had off shows off. Once every saved computer has registered, the phone saves those values as its own and sends them everywhere. Then comes one row per computer: On, Can't reach this computer, No Apple push key on this computer (load it in Settings › Integrations on any computer, and key sync copies it), Notifications are off in iOS Settings, Update Pane on this computer, or the computer's own message. Sign out in Machine details revokes that computer's registration, after any registration already on its way, and stops new ones before it deletes the profile.

Tapping a notification opens `/open?host=…&paneId=…&panelId=…` (plus `notifyId=…` for a Notify question). That screen switches to the matching saved host if it isn't the active one, then replaces itself with the pane, or with the question's sheet. It never connects to a host this phone hasn't paired with. On iOS the host's routing keys sit beside `aps`, so expo-notifications exposes them only as `trigger.payload`, not `content.data`. `parsePushTarget` reads both.

**Links** (rewritten in `src/app/+native-intent.tsx`):

| Link | Opens |
| --- | --- |
| `https://runpane.net/pair#s=…&c=…&n=…` and `pane://pair#…` | **Pair with <computer>** (`features/pairing/RelayPairPrompt.tsx`). It pairs only after you tap Pair. `pane://pair` names Pane's domain unless its fragment carries `d=<domain>`. |
| `pane-remote://<code>` | The pairing screen with the code filled in (`features/pairing/deepLink.ts`). It connects only after you tap Connect. |
| `pane://pane/<paneId>?host=<base URL or profile id>&panel=<panelId>` | That pane, switching hosts first. Without `host` it opens the pane on the active host. |

### Notify questions

When an agent asks through Notify ([Pane Notify](../docs/PANE_NOTIFY.md)), the host sends every phone with "Needs Input" on one alert per question, about 90 seconds after it arrives and only if it is still waiting; answering it, closing it or turning Approvals off first cancels the alert ([Alerts](../docs/PANE_NOTIFY.md#alerts)). The title is the Pane's name (the folder's, for an agent outside Pane) and the body says only "<name> has a question". It replaces that Pane's "is blocked" alert. The app registers with `notifyButtons: true` (Pane app 1.1+), which tells the host this build draws the buttons.

**The sheet.** Tapping the alert, or the question's row under **Questions** at the top of the pane list, opens `pane/[paneId]/notify?notifyId=…`, or `notify/[notifyId]` for a question from outside any Pane (`src/features/notify/NotifySheet.tsx`). It reads `notify:remote-snapshot`, refetches on `notify:shared-changed`, and answers, notes and Undo go through `notify:remote-command`. A Pane with a waiting question shows the "Needs input" dot. While the host holds an answer for Undo (3 s), the sheet shows it with Undo, like every other screen: "Sent to <agent>" when this phone answered, from the moment the host accepts it, and "Answered on <device>" otherwise. An Undo on any screen brings the question back. When the host passes this phone's answer on, the sheet closes; a question answered elsewhere then shows "Already answered on <device>", and one whose agent gave up shows "<agent> stopped waiting". The phone's name (`expo-constants` `deviceName`) is sent as the device label, so desktops show "Answered on <phone>". iOS 16+ reports only "iPhone" without Apple's user-assigned-device-name entitlement.

**Alert buttons** (`src/features/notify/notifyBackground.ts`, loaded from `index.ts` before the router so a background launch runs it):

| Question | Buttons |
| --- | --- |
| `approve` | Approve, Deny (destructive) |
| `options` with 1 to 3 choices | One per choice, labelled with it, recommended first |
| `ask` | Reply, with a text field |
| `options` with 4 or more choices | None; a tap opens the sheet |

Buttons work on a locked phone: no action asks for Face ID or the passcode. A press reads the saved host from secure storage and posts `notify:remote-command` straight to `/invoke`, without opening the event stream. Nothing shows when it works. When it fails, the phone posts a short alert: "Not sent: can't reach <host>. Try again when it reconnects." (the question's alert stays, so the button can be pressed again), or the host's refusal, such as "Already answered on <device>. Nothing was sent.". When the host's reply is lost or takes over 15 s, the answer may have arrived, so the alert says "Your answer may have reached <host>. Open the question to check before answering again." and tapping it opens the sheet. A press is never retried automatically. `IOS_BUTTONS_OPEN_APP` in `src/features/notify/notifyActions.ts` is the D-13 switch: set it to `true` and every iPhone button opens Pane and sends from there. Android always answers in the background.

- **iPhone.** The approve and ask categories are registered at app start. The host gives a short options alert `mutable-content: 1`, and the notification service extension in `targets/notify-service` (built by `@bacons/apple-targets` at prebuild, bundle ID `com.dcouple.pane.mobile.notify-service`) registers `pane.notify.options.<notifyId>` with that question's labels as the alert arrives. When the extension fails, the alert has no buttons and a tap still opens the sheet. A button press launches Pane in the background; iOS gives it a few seconds to send.
- **Android.** The host sends a data-only, high-priority message. The background task (`expo-task-manager`) draws the alert with its buttons on the "Questions from agents" channel, tagged with the host's `notifyTag`, and handles button presses while Pane is closed.
- **Stale alerts.** When a question is answered elsewhere, the host sends a silent clear (`notifyClear`), and the task removes that alert. This is reliable on Android and best effort on iPhone (`content-available`, `enableBackgroundRemoteNotifications`). The app also removes alerts for questions that its snapshot no longer shows waiting. Opening a Pane removes its "is blocked" and "finished" alerts, but question alerts stay until the question is answered.

**Try it on the Simulator.** A host reports push as ready only when `PANE_APNS_*` is set. For registration and the permission prompt, a throwaway P-256 key is enough (`openssl ecparam -name prime256v1 -genkey -noout | openssl pkcs8 -topk8 -nocrypt -out FakeAuthKey.p8`). ### Firebase config (google-services.json)

`native/google-services.json` is gitignored. It is the Firebase Android app config for `com.dcouple.pane.mobile` in the `pane-pwa-preview` project. It identifies the app and cannot send pushes. Get it locally from the Firebase console (Project settings, Your apps, Android) or with `firebase apps:sdkconfig ANDROID <app-id> --project pane-pwa-preview -o native/google-services.json`.

CI reads it from the `PANE_ANDROID_GOOGLE_SERVICES_JSON` repository secret, base64-encoded. `.github/workflows/native-android.yml` decodes it into `native/google-services.json`, then builds the Android dev client. Pull requests and pushes to `main` build only when the Expo Android fingerprint differs from the base (the PR's base or the commit before the push) or the workflow changed; pull requests build only `arm64-v8a`, and pushes build all four ABIs. A weekly run and manual runs always build all four. The step fails if the secret is missing or not for this package; fork PRs, which get no secrets, build without FCM. To rotate it:

```bash
base64 < native/google-services.json | tr -d '\n' | gh secret set PANE_ANDROID_GOOGLE_SERVICES_JSON -R greenfield-inc/Pane
```

## Over-the-air updates

Release builds of the app download new JavaScript from Pane's update server, so a JavaScript change reaches installed phones without a new TestFlight or store build. The app uses `expo-updates` against a small self-hosted server: the Cloud Run service `pane-native-updates` (`updates.url` in `app.json`), which serves one manifest per runtime version and platform (`deploy/native-updates/`).

**What ships over the air.** Anything in the JavaScript bundle: `src/`, `../shared/`, and JavaScript-only packages. Native code needs a store build: a package with iOS or Android code, a config plugin, a setting in `app.json` that prebuild writes into the native projects, or `targets/`. A native change bumps `runtimeVersion` in `app.json`, for example from `1.2` to `1.3`, and ships in a store build with that runtime. Phones get only updates for their own `runtimeVersion`, so after a bump, OTA reaches a phone once it installs the new build.

The `Native Runtime` PR check compares the Expo fingerprint of native code (`fingerprint.config.js`) at the base and the head. It fails when native code changed without a bump. With a bump it passes and adds the `native-change` label (on a fork PR, a maintainer adds it). Version and build numbers don't count as native changes.

**Publishing is automatic.** Every push to `main` that touches `native/`, `shared/`, `pnpm-lock.yaml`, the update server or its workflow runs `Native OTA Updates` (`.github/workflows/native-updates.yml`). It runs `expo export`, writes the manifests with `scripts/build-updates.mts`, and deploys a new image. When a deploy fails, run that workflow again from the Actions tab on `main`.

An update is dated with its commit's committer date. A phone loads only an update newer than the one it runs, including the bundle built into the app, so a successful re-run of the same commit sends phones nothing new. Make store builds from the tip of `main`: an update dated before the build never loads on it.

**When it applies.** At launch, the app checks the server and downloads a new update in the background. It runs from the next cold start. Settings › About shows what is running: `Version 1.2 · Built-in` for the bundle inside the app, or `Version 1.2 · Update a1b2c3d · Oct 28`, where `a1b2c3d` starts the update id (the workflow run prints one per platform) and the date is the commit date. Tap the row to check now. Once an update is downloaded, the row says **Restart to update**, and tapping it switches to the update. Debug and dev-client builds load JavaScript from Metro and show `Development build`.

**Rolling back.** Revert the change on `main`, which publishes a newer update. Shifting Cloud Run traffic to an earlier revision does nothing for phones, because they load only a newer update. If an update throws before its first screen, the phone marks it failed and reloads the last update that launched.

**Testing locally.** Build a release app that asks a server on your computer, change some JavaScript, then serve an export of it:

```bash
cd native
export PANE_UPDATES_URL=http://127.0.0.1:8099/manifest
npx expo prebuild --clean --platform ios && npx expo run:ios --configuration Release
# Android: npx expo prebuild --clean --platform android && npx expo run:android --variant release

# Change something visible in src/, then export it.
D=/tmp/pane-ota.noindex
pnpm exec expo export --platform ios --platform android --output-dir $D/dist
pnpm exec expo config --type public --json > $D/expo-config.json
# --created-at now: phones ignore an update older than their build.
node scripts/build-updates.mts --dist $D/dist --config $D/expo-config.json \
  --base-url http://127.0.0.1:8099 --out $D/ctx/site --created-at "$(date -u +%FT%TZ)"
cp ../deploy/native-updates/Dockerfile ../deploy/native-updates/nginx.conf $D/ctx/
docker build -t pane-native-updates:local $D/ctx
docker run -d --rm --name pane-native-updates -p 8099:8080 pane-native-updates:local   # stop: docker stop pane-native-updates
adb reverse tcp:8099 tcp:8099   # Android emulator or USB phone; on iOS, use the Simulator
```

Launch the app once to download the update and again to run it. `PANE_UPDATES_URL` replaces `updates.url` for that build; an `http://` URL also allows plain HTTP on Android. `expo run` only regenerates `ios/` or `android/` when the folder is missing, so the `prebuild --clean` is what writes the URL into the native project, with or without the variable. Before building anything you ship, run `unset PANE_UPDATES_URL` and `npx expo prebuild --clean` again. Check the server with `curl -i -H 'expo-platform: ios' -H 'expo-runtime-version: 1.2' http://127.0.0.1:8099/manifest`: it answers `200` with `expo-protocol-version: 1` and the manifest, or `204` when it has no update for that runtime.

## How the code is organised

| Path | What goes there |
| --- | --- |
| `index.ts` | The app entry: Notify's background handling, then `expo-router/entry`. |
| `src/app/` | Expo Router routes only. Each file is a screen, `_layout.tsx` files are navigators. |
| `src/features/<area>/` | Components, hooks and logic for one feature (pairing, panes, terminal, …). |
| `src/ui/` | The design system: `Screen`, `ListRow`, `ListSection`, `Button`, `TextField`, `EmptyState`, `ErrorState`, `Skeleton`, `Sheet`, `Text`, `Icon`. Import from `@/ui`. |
| `src/theme/` | Colors (light and dark, from the desktop app's default themes), spacing, radius, typography. `useTheme()`. |
| `src/daemon/` | Connection to the active host: `DaemonProvider`, `useDaemon()`, `useInvokeQuery`, `useInvokeMutation`, `useDaemonEvent`, the TanStack Query client. |
| `src/auth/` | Saved hosts in secure storage (`useHostsStore`), pairing verification. |
| `../shared/` | Types and logic shared with the desktop app and the PWA. Import as `@shared/...`. |

See `AGENTS.md` for conventions.
