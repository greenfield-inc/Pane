Pane agent context

For people:
Open a Session for each workstream and tell its agent what you want, in plain words. It plans the work, starts a Pane for each feature, and runs the builders, reviewers and QA as tabs inside them, so you don't have to. Anything that needs you, like a decision, an approval or a merge, waits for you in Approvals while everything else keeps moving. When a feature is done, archiving its Pane cleans up its worktree and files for you.

For agents:
In Pane, work flows from a Session to Panes to tabs. A Session is a workstream: the person or an orchestrator opens it, and every Pane created or adopted from inside it joins it. When you are in one ($PANE_SESSION_DIR is set: you orchestrate it or your Pane belongs to it), start new Panes from there (each result's `association` names the Session they joined); when you are in none, work with several parts starts a new Session. Each feature gets one Pane, a git worktree on its own branch, and everything for that feature (the agent that builds it, its reviews, QA and fixes) runs as tabs inside it. Scratch files go in $PANE_SCRATCH_DIR inside the Pane. When the feature is done, archive the Pane and Pane cleans up its worktree, tabs and scratch files. When you need the person, ask through Approvals (a Session worker reports blocked to its orchestrator instead).

Working in Pane:
- Session: where a workstream lives, and the default home for orchestrated work. Its folder ($PANE_SESSION_DIR) holds plans, notes and reports.
- Pane: one per feature (one worktree, one branch). Before creating one, find the feature's Pane (`runpane panes list --json`, match the branch) and create one only when none exists.
- Tab: reviews, review reruns, QA, fixes and follow-ups for a feature go in new tabs in its Pane (`runpane panels create --pane <id>`), never a new Pane or a plain `git worktree`.
- Scratch: in Pane, put temporary files, clones, captures, downloads, logs and test instances (an isolated PANE_DIR and HOME for QA) in `$PANE_SCRATCH_DIR`, not /tmp or your tool's own scratchpad. When the feature is done, archive the Pane and Pane cleans it up.
- Profiles: a profile is a team and a fixed workflow Pane runs from its file (docs/PROFILES.md). Once Profiles is on (Settings › Advanced › Profiles), `runpane profiles list` and `runpane profiles launch <name> --prompt <text>` start one; in a profile step's tab, end the step with `runpane report --outcome "<one of the step's outcomes>"`, which the step's first message names.

Pane runs coding agents in parallel git worktrees. A Pane is a visible workspace for one feature or PR, with its own Pane-managed git worktree and branch; a panel is a terminal tab in a Pane and shares its worktree; an agent is a CLI process running in a panel.

Rules:
- Start with `runpane doctor --json` to understand wrapper, platform, daemon reachability, and the next safe commands before mutating Pane state.
- In a Pane repository checkout, if `runpane` is not on PATH, build the local wrapper with `pnpm --filter runpane build` and run it with patched Node 22.23.4+ (22.x), 24.22.1+ (24.x), or 26.12.1+ (26.x), for example `node packages/runpane/dist/cli.js doctor --json`.
- Happy path for any user request to use Pane/RunPane: run `runpane doctor --json`, read `runpane agent-context --json`, resolve or add the saved base repo, then route by the rule If the work's branch already has a Pane (find it with `runpane panes list --repo <repo> --json` by matching the PR's head branch against `git -C <worktreePath> branch --show-current`), open a new agent tab in it with `runpane panels create --pane <id> --agent <agent> --initial-input "<task>" --source agent --no-focus --wait-ready --yes --json`; only when the branch has no Pane yet, create one with a complete command such as `runpane panes create --repo <repo> --name <name> --agent <agent> --prompt "<task>" --source agent --no-focus --wait-ready --yes --json` (the new Pane is pinned by default; add `--no-pinned` for a throwaway Pane, add `--base-branch <ref>` to branch from something other than the repository default, or use `--tool-command <command>` instead of `--agent <agent>`), then validate with `panels wait` or `panels screen`. For long-lived supervision, use `runpane watch --follow` instead of polling wait or screen.
- Treat Pane as the user's visible cockpit for watching/co-driving work. Do not create Panes or panels for private delegation unless the user asked for visible Pane orchestration or the result should appear in the Pane app.
- Register the saved base repository once with `repos add`; do not register a pre-created worktree as a separate repo unless the user explicitly asks.
- Use `panes create` only when the work's branch has no Pane yet (new work, or an existing PR with no Pane), since each new Pane creates a worktree. Every later agent for that branch opens as a new tab in its Pane with `panels create --pane <id>`, never a new Pane. Tabs share one checkout: only the implementer changes the branch or HEAD, one writer at a time; review, audit and QA tabs never run `git checkout`, `reset` or `stash`.
- For private background decomposition, use your normal subagent/worktree mechanism instead of Pane.
- Skill routing: Pane's skills live in `<PANE_DIR>/skills/pane-chat/skills/`, and the Pane Chat entry point is `<PANE_DIR>/skills/pane-chat/pane-orchestrator/SKILL.md`; read the skill that matches the request, such as `discussion`, `create-ticket`, `tdd`, `prepare-pr`, or `review`.
- When an agent creates Panes or panels, pass `--source agent --no-focus --wait-ready --yes --json` unless the user explicitly wants focus moved; `panes create` pins the new Pane into the UI's favorite/pin set by default, so no follow-up `panes pin` call is needed and `--no-pinned` is the opt-out for throwaway Panes.
- Use `runpane agent-context --json` for the full agent-facing CLI context, or `runpane agent-context --command <command> --json` for one detailed command definition.
- For `agent-context --command`, use canonical spaced names like `panes create`; copied forms like `panes.create` or `runpane panes create` are accepted too.
- Use `runpane repos list --json` to find the saved repository when unsure after doctor shows the daemon is reachable.
- Read and change a repo's Project Settings (build, run, and archive scripts, worktree folder, environment variables) with `runpane repos get` and `runpane repos update`; never edit Pane's database by hand.
- When a command needs a secret (an API key, a token), run it with `runpane secrets exec --project <project> -- <command>`. If the secret is missing, ask the person with `runpane secrets request`; never ask them to paste a secret into the chat, and never print one. For a secret from 1Password, ask with `runpane secrets lease` and wait; when `secrets exec` fails with SECRET_LEASE_ENDED, run the next step it names.
- If WSL cannot reach Pane, the user may be running Windows Pane; try `/mnt/c/Users/<you>/.pane/bin/runpane doctor --json`, or with an older Pane build `powershell.exe -NoProfile -Command 'Set-Location $env:TEMP; runpane doctor --json'`.
- If the repository exists on disk but is not saved in Pane, use `runpane repos add --path <repo> --yes --json` before creating panes.
- Use `runpane agents doctor --agent <codex|claude|cursor|opencode|pi> --repo <selector> --json` when agent availability differs across host, Windows, WSL, or repo environments.
- Use `runpane panes create --wait-ready` to create Panes, wait for each agent's input box, and verify its starting message in one call.
- Use `runpane panels screen` for compact current state, including Claude and Codex composer state. Use `panels wait` for create-time readiness or text checks. Use `runpane watch --follow` to block on workspace transitions (READY, BLOCKED, IDLE, STUCK, EXIT) without polling, or `runpane watch --until-event` to exit on the first one. Use `panels submit` to send and submit a new turn. Use `panels submit-composer --strategy auto` only for a composer that was filled separately.
- Use `runpane panels input` only when exact bytes are required, such as Ctrl-C or handcrafted terminal input.
- Pane terminals draw inline images: sixel, iTerm2 inline images, and the kitty graphics protocol. Tools that need kitty graphics, such as terminal-browser and terminal-doom, run inside a Pane panel; `runpane doctor --json` reports the exact list under `terminal.graphicsProtocols`.
- After creating Panes or sending terminal input, validate with `panels wait` or bounded `panels screen`. For a harness that consumes streaming output, use `runpane watch --follow` (with `--session <id>` for a Session); its named consumer applies settling and batching. Adding numeric --since leaves it unnamed and bypasses cadence; --as cannot be combined with --since. A harness that wakes only when a process exits uses `runpane watch --as <name> --until-event --json` and runs it again after each event. Single-event waits deliver immediately without follow cadence. Never pipe `--follow` into `grep -m1` or `head`.
- When several agents share one resource, such as a test account, name a lock in their prompts: each worker runs `runpane lock acquire --name <name> --ttl 30m --wait 1800000 --json` before using it and `runpane lock release --name <name>` after.
- Loops (`runpane loops create`) run a task on a cron schedule, each run in a new Pane or, with `--session`, as a message to a Session's agent. They are for large recurring jobs, such as a nightly bug sweep, and run at most once an hour. For a short wait, use your agent harness's own sleep and wake instead.

Tools:
- doctor: Report wrapper, platform, installed Pane, and daemon reachability before an agent mutates Pane state.
  Args: --json, --pane-dir <path>, --pane-path <path>
- agent-context: Print token-efficient Pane command context for coding agents.
  Args: --command <command>, --json
- agents doctor: Check whether Codex or Claude is available in the repo environment Pane will use.
  Args: --agent <codex|claude|cursor|opencode|pi>, --repo <selector>, --json
- repos list: List repositories saved in the running Pane app.
  Args: --json, --pane-dir <path>
- repos add: Register an existing git repository with the running Pane app.
  Args: --path <path>, --name <name>, --yes, --json, --dry-run, --pane-dir <path>
- repos get: Show a saved repository's Project Settings and the scripts Pane will run.
  Args: --repo <selector>, --json, --pane-dir <path>
- repos update: Change a saved repository's Project Settings: scripts, worktree folder, name, IDE command, system prompt, and environment variables.
  Args: --repo <selector>, --build-script <script>, --run-script <script>, --archive-script <script>, --worktree-folder <path>, --env <json>, --env-remove <name,...>, --name <name>, --clear <setting,...>, --from-json <path|->, --yes, --dry-run, --json
- repos rename: Rename a repository saved in the running Pane app.
  Args: --repo <selector>, --name <name>, --yes, --json, --pane-dir <path>
- secrets list: List Pane secrets: project, name, time and machine, plus 1Password references and live leases. Never a value.
  Args: --project <project>, --json
- secrets exec: Run a command with Pane secrets in its environment.
  Args: --project <project>, --only <name,...>, --env <VAR=NAME>, --file <name>, -- <command>...
- secrets request: Ask the person for a secret on a masked card; returns saved or declined, never the value.
  Args: --project <project>, --name <name>, --title <text>, --reason <text>, --json
- secrets lease: Ask the person to lease 1Password-backed secrets; returns the lease id and end time, never a value.
  Args: <NAME>..., --project <project>, --reason <text>, --json
- panes list: List Pane sessions, optionally scoped to a saved repository.
  Args: --repo <selector>, --json, --pane-dir <path>
- panes cost: Report estimated token cost per Pane, with per-model breakdown and cache efficiency.
  Args: --repo <selector>, --pane <pane-id>, --json, --pane-dir <path>
- panes create: Create a Pane (a new worktree) only when the work's branch has no Pane yet; for review, audit, fix or QA on existing work use `panels create --pane <id>`.
  Args: --repo <selector>, --name <name>, --agent <codex|claude|cursor|opencode|pi>, --tool-command <command>, --prompt <text>, --initial-input-file <path|->, --from-json <path|->, --source <user|agent>, --pinned, --no-pinned, --no-associate, --no-focus, --focus, --wait-ready, --ready-timeout-ms <ms>, --concurrency <count>, --yes, --json
- panes archive: Archive a Pane exactly like the UI Archive action, including safe removal of its Pane-managed git worktree, or archive every merged Pane in a Session.
  Args: --pane <pane-id>, --session <id|name>, --merged, --closed, --source <user|agent>, --force, --remove-worktree, --dry-run, --yes, --json
- panes pin: Declaratively pin a Pane (the Pane UI's favorite/pin star) without changing focus.
  Args: --pane <pane-id>, --yes, --dry-run, --json
- panes unpin: Declaratively unpin a Pane (the Pane UI's favorite/pin star) without changing focus.
  Args: --pane <pane-id>, --yes, --dry-run, --json
- panes rename: Rename a Pane without changing its worktree, branch, panels, or focus.
  Args: --pane <pane-id>, --name <new-name>, --yes, --dry-run, --json
- panes focus: Raise the Pane window and select a Pane (and optionally a panel) on explicit user request.
  Args: --pane <pane-id>, --panel <panel-id>, --source <user|agent>, --yes, --json
- panels create: Open reviewer, QA, fix or helper agent tabs inside an existing Pane; they share that Pane's worktree. The default for any later agent on existing work.
  Args: --pane <pane-id>, --agent <codex|claude|cursor|opencode|pi>, --tool-command <command>, --source <user|agent>, --no-focus, --focus, --wait-ready, --yes, --json
- panels open: Show the user an HTML page, plan, report, dev server URL, or file as a tab in split view beside the agent.
  Args: --pane <pane-id>, --url <url>, --file <path>, --title <title>, --split, --tab, --no-focus, --source <user|agent>, --yes, --json
- panels close: Close a tab an agent opened once it no longer matters; refuses the person's tabs, busy agents and unsent input.
  Args: --panel <panel-id>, --dry-run, --force, --source <user|agent>, --yes, --json
- panels list: List tool panels inside a Pane session.
  Args: --pane <pane-id>, --json, --pane-dir <path>
- panels output: Read recent terminal output from a panel.
  Args: --panel <panel-id>, --limit <count>, --json, --pane-dir <path>
- panels screen: Read a compact current-screen view from a terminal panel.
  Args: --panel <panel-id>, --limit <count>, --json, --pane-dir <path>
- panels input: Send input bytes to a terminal panel.
  Args: --panel <panel-id>, --text <text>, --input-file <path|->, --yes, --json, --pane-dir <path>
- panels submit: Send text plus terminal Enter to a terminal panel.
  Args: --panel <panel-id>, --text <text>, --input-file <path|->, --yes, --json, --pane-dir <path>
- panels submit-composer: Submit an agent composer with the key for its current state.
  Args: --panel <panel-id>, --strategy <auto|codex-ctrl-enter|enter|tab>, --yes, --json
- panels wait: Wait for terminal initialized, ready, idle, or text state with compact output.
  Args: --panel <panel-id>, --for <condition>, --contains <text>, --timeout-ms <ms>, --interval-ms <ms>, --json, --pane-dir <path>
- panels resume: Restart a stopped terminal panel in place (same panel id), resuming its agent's conversation.
  Args: --panel <panel-id>, --session <id|name>, --all-stopped, --concurrency <count>, --wait-ready, --ready-timeout-ms <ms>, --yes, --json, --pane-dir <path>
- watch: Wait for workspace events from the durable daemon journal; follow uses conservative cadence and quiet expiry by default.
  Args: --follow, --until-event, --session <id|name>, --self-test, --kinds <kind,...>, --json
- notify: Ask the person a question wherever they are and wait for the answer; prefer it to asking in the terminal.
  Args: --ui <options|approve|ask|info>, --title <text>, --choices <json>, --links <json>, --resume <id>, --json

Detailed definitions: runpane agent-context --command <command> [--json]
